# NOTE ON RULE 3 vs RULE 1: their safety tests are OPPOSITE. A RULE 1 element with no containing
# block teleports into the first viewport, so "below the fold" is NOT a defence. A RULE 3 element
# sits at its natural in-flow position, so "it and everything below it are below the fold" IS a
# valid defence. Several rows rely on that.
#
# THREE MODEL GAPS the triage exposed, all worth knowing before trusting a RULE 3 verdict:
#   1. FIXED in this change — the lint modelled only critical-css.liquid as first-paint CSS and
#      ignored snippets/css-overrides.liquid (~98KB, inline in <head> at layout/theme.liquid:626,
#      Liquid nesting depth 0). That alone produced the product__badge and cart__items__remove
#      false positives. Both sheets are now parsed.
#   2. NOT fixed — the lint assumes every template uses layout/theme.liquid. templates/password.json
#      declares "layout": "password", and layout/password.liquid loads theme.css as a RENDER-BLOCKING
#      link with no critical-css inline and no media=print swap, so the whole deferred-CSS bug class

#   3. NOT fixed — the lint treats every deferred sheet as loading on every template. Several are
#      Liquid-gated (theme-search.css at layout/theme.liquid:565, theme-cart.css at :556), so a

#   4. NOT fixed — build_outer_context propagates a section's SCHEMA class across {% render %}

# CROSS-FILE SUPPRESSION ADDED 2026-08-06 (bd nf3j). A snippet sits inside whatever markup encloses
# its render callsite, so a containing block can come from a wrapper in the CALLING file:
# css-overrides positions `.cart__template .cart__items__row`, but `.cart__template` is on a wrapper
# in sections/cart.liquid, one render above snippets/cart-line-items.liquid.
#
# That context is used for SUPPRESSION ONLY, never detection, and the asymmetry is deliberate. The
# union across callers is a fiction: snippets/icon-bin.liquid is rendered both from the footer and
# from inside .cart__items__remove, so a merged set satisfies `.footer__title .icon{position:absolute}`
# from one caller while offering `.cart__items__remove` as the late ancestor from another - an
# ancestry that never co-occurs on a real page. Feeding it to the detection side invented three
# findings when tried, so detection stays on the schema-class context, which is deterministic (one
# class per section). Being over-broad on the suppression side can only remove a finding, never
# invent one. Per-caller contexts were also tried and made things worse, not better.
